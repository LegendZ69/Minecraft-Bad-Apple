# v1.1.0 — provenance and cloud verification

Mod version **1.1.0** targets **Minecraft Java Edition 1.21.1**, with Java 21,
Fabric Loader 0.16.5 or newer, and Fabric API for Minecraft 1.21.1. It is not a
port to another Minecraft version.

**Release verification status: original-media and exact-JAR runtime checks pending.** Unit tests,
the reproducible Fabric JAR, and synthetic Minecraft controls/stereo-audio checks
have passed. The original source has also passed exhaustive conversion checks;
its full Minecraft playthrough and the production-namespace check are still
pending. The release tag and packaged
build information identify the final source revision.

## Changes from v1.0.0

- Explicit source selection for the official label upload, original NicoVideo
  animation, and user-linked YouTube reference; no silent substitution.
- Recorded source provenance and a bounded public reference-access report.
- Exhaustive archive verification against the local source, with a saved report.
- Verified conversion of the original NicoVideo animation: all 6,573 decoded
  frames, relative timestamps, and normalized audio match the acquired source.
- Clearly synthetic video/audio fixtures for repeatable conversion and runtime
  testing without redistributing the original animation or recording.
- An isolated Minecraft client smoke-test harness and versioned release records.
- Add an isolated production-namespace test using Fabric's official
  [production run tasks](https://docs.fabricmc.net/develop/loom/production-run-tasks),
  binding the tested mod JAR to its SHA-256. This additional check is pending;
  it is not an authenticated Minecraft Launcher test.
- Replace the inherited native `Clip` output with a `SourceDataLine` adapter
  requesting a 20 ms buffer. Cloud Linux checks also set
  `PULSE_LATENCY_MSEC=20`; see the README for the tested launch configuration.
- Correct stale audio-clock readings after backward seeks, restart, and looping,
  and preserve elapsed time when an unresponsive device falls back to silent
  playback. Timestamp native audio queries after they return so blocking device
  reads do not falsely trigger silent fallback.
- Decode PNGs through an expandable native-buffer path instead of copying a
  complete encoded frame onto LWJGL's small native stack. This fixes the
  inherited v1.0.0 failure on larger PNG frames; decoder termination is now
  surfaced instead of silently leaving a frozen texture.
- Add full-run texture freshness/progress checks so an unchanged old texture
  cannot pass solely because its stored GPU pixels still match that old frame.
  Deterministic and synthetic Minecraft controls/audio checks pass; full-length
  original-media playback remains a separate check.

## Native audio buffering diagnosis

The baseline's native `Clip` path showed abnormal buffer/clock behavior in cloud
Linux tests. OpenJDK's
[DirectAudioDevice](https://github.com/openjdk/jdk21u/blob/master/src/java.desktop/share/classes/com/sun/media/sound/DirectAudioDevice.java)
requests a 1,000 ms clip buffer. Its
[Linux ALSA backend](https://github.com/openjdk/jdk21u/blob/master/src/java.desktop/linux/native/libjsound/PLATFORM_API_LinuxOS_ALSA_PCM.c)
estimates position from buffer availability, while
the [ALSA PulseAudio plugin](https://github.com/alsa-project/alsa-plugins/blob/master/pulse/pcm_pulse.c)
clamps writable space used to advance its simulated ring buffer. The completed
[four-case probe](https://github.com/LegendZ69/Minecraft-Bad-Apple/actions/runs/34177059058)
supports the low-latency configuration: only the 20 ms `SourceDataLine` plus
`PULSE_LATENCY_MSEC=20` produced the intended nine seconds of non-silent output
in both channels, with 97.78% of audible 100 ms windows within 440 ± 20 Hz.
The other cases showed start/seek lag and shortened captured output. Four
successful job exits did not mean four correctly behaving configurations.

## Download and run

1. Download `minecraft-bad-apple-1.1.0.jar` from the
   [v1.1.0 release](https://github.com/LegendZ69/Minecraft-Bad-Apple/releases/tag/v1.1.0)
   and put it in the Minecraft instance's `mods` folder alongside Fabric API.
   Install the normal mod JAR, not a sources JAR or test artifact.
2. Download the matching source/tools bundle or check out tag `v1.1.0`. With
   Python 3.10+, FFmpeg, and ffprobe available, prepare and verify an authorized
   local reference:

   ```sh
   python tools/prepare_video.py "reference.mp4" --output bad_apple.bapple
   python tools/verify_archive.py bad_apple.bapple --source "reference.mp4" --report verification.json
   ```

3. Copy `bad_apple.bapple` to `<instance>/badapple/bad_apple.bapple`. Start
   Minecraft Java 1.21.1 with Fabric, join a world, and run `/badapple play`.
4. Use `/badapple status` to inspect playback and `/badapple place native` for
   one source pixel per block of screen area. Pause with `/badapple pause`.

For explicit official-source download options, access limitations, and media
rights boundaries, read [reference sources](../REFERENCE_SOURCES.md). Original
animation/audio is not an asset in this public release; a synthetic fixture is
not the requested Bad Apple!! animation. Evidence may include selected in-game
screenshots and complete metadata/measurement reports, not the full source video
or its converted playback archive.

## Reproduce the cloud checks

Use JDK 21, Gradle 8.8, Python 3.10+, FFmpeg, and ffprobe. A graphical Minecraft
client also needs an OpenGL-capable display; Linux cloud runs use a virtual
display and software rendering configured by CI.

```sh
gradle build
python -m unittest discover -s tests -v
python tools/generate_fixture.py --output build/synthetic.mkv
python tools/prepare_video.py build/synthetic.mkv --output build/smoke-game/badapple/smoke.bapple
python tools/verify_archive.py build/smoke-game/badapple/smoke.bapple --source build/synthetic.mkv --report build/archive-verification.json
gradle runSmokeClient
```

The smoke harness is isolated in `src/smoke`; it is not part of the installable
mod. The fixture path above is intentional. Run the client under the display
setup used in the workflow, and inspect its saved reports and logs rather than
inferring success merely from a process having started. Preserve the source,
archive, verification report, and runtime evidence together when reproducing a
result.
